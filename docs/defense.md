# Підготовка до захисту

План відповідає розділу 10 умови («Критерії приймання та захисту»).

## 1. Демонстрація на нових прикладах

Прикладів нижче **немає** у `examples/`, `tests/` чи `conformance/` — їх можна набрати
на захисті або попросити викладача дати свої.

```
// мінімум з трьох чисел
begin
  if A > B then M := B else M := A;
  if M > C then M := C else skip
end
```
`sipl run min3.sipl -s A=5 -s B=2 -s C=9` → `M = 2`

```
// кількість цифр числа N > 0 (у SIPL немає ділення — ділимо на 10 відніманням)
begin
  K := 0;
  while N > 0 do
  begin
    Q := 0;
    while N > 9 do begin N := N - 10; Q := Q + 1 end;
    N := Q;
    K := K + 1
  end
end
```
`sipl trace digits.sipl -s N=405` → `K = 3`; у trace видно вкладені цикли.

```
// множення через додавання
begin P := 0; while B > 0 do begin P := P + A; B := B - 1 end end
```
`sipl tree mul.sipl --kind both --format svg -o mul.svg` — показати, як вузол `While` в AST
відповідає `<while statement>` у дереві виводу.

Негативні сценарії: прибрати `else`; написати `=` замість `:=`; написати `X < Y`, `and`
чи `/` (парсер пояснить, що цього немає в SIPL, і підкаже заміну); запустити без
`-s A=...` (невизначена змінна, код 3); `begin while 0 = 0 do skip end` (ліміт кроків, код 4).

Дерева: `sipl tree FILE --kind both --format svg -o compare.svg` (обидва дерева поруч),
`sipl tree FILE --rules` (дерево виводу з номерами правил БНФ у терміналі).

## 2. Архітектура (як проходять дані)

`текст → Lark LALR (граматика sipl.lark, keep_all_tokens) → ParseNode (дерево виводу,
SourceSpan у кожному вузлі) → _AstBuilder → AST (власні dataclass) → Interpreter.events()
(генератор подій) → run/trace → CLI (текст або JSON)`. Детально — `docs/architecture.md`.

Ключові відповіді:
- *Чому AST не є деревом Lark?* — Lark повертає лише конкретне дерево; ми його
  конвертуємо у власні типи, щоб API не залежав від бібліотеки (критерій CORE-02).
- *Чим дерево виводу відрізняється від AST?* — у дереві виводу є всі нетермінали БНФ
  і всі токени (ключові слова, `;`, дужки, ланцюги `<arith expr>→<term>→<factor>`);
  в AST лише смислові вузли. `power.sipl`: 65 проти 18 вузлів.
- *Чому граматика саме така?* — вона рівно відповідає БНФ курсу (P1, S1–S6, A1–A6,
  B1–B5). БНФ неоднозначна, тому записана в однозначній формі: рівні пріоритету
  `aexp` (+, −) → `term` (*) → `factor`, `bexp` (∨) → `bterm` (¬) → `bfactor`;
  ліва рекурсія дає лівоасоціативність; межі then/else/while — як у Pascal.
- *Чому немає `<`, `and`, ділення?* — їх немає в БНФ курсу. Те саме виражається
  засобами мови: `X < Y` ≡ `Y > X`, `b1 and b2` ≡ `¬(¬b1 ∨ ¬b2)`, ділення — відніманням
  (приклад `examples/valid/divmod.sipl`).
- *Як працює контроль нескінченних циклів?* — лічильник кроків в інтерпретаторі,
  `ProgramFinished(status="step_limit")`, CLI повертає код 4.
- *Як trace придатний для debugger?* — інтерпретатор є генератором: виконання йде
  лише коли беремо наступну подію; кожна подія має `node_id` та `span`.

Чистий venv → `pip install -e ".[dev]"` (або wheel з релізу) → `sipl run ...`.
CI робить те саме на Python 3.10–3.13 і окремо перевіряє зібраний wheel.

## 6. Теоретична основа

- БНФ і дерево синтаксичного виводу (ПР 1): програма синтаксично коректна ⇔ існує
  дерево виводу з кореня `<програма>`, крона якого — текст програми; LALR-парсер будує
  саме це дерево (права частина кожного вузла = правило граматики).
- Семантика операторів — перетворення станів: стан = часткове відображення змінних
  у ℤ; присвоювання змінює одне значення, композиція — послідовне застосування,
  `while` — повторення, поки умова істинна. Невизначеність (нема змінної в стані,
  незавершення) обробляється явно.
- Межі автоматизації: незавершуваність загалом нерозв'язна, тому використано ліміт
  кроків — це евристика, а не доведення нескінченності циклу.
